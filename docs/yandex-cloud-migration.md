# Техническое задание: перенос ManagerPlanner в Yandex Cloud

## Цель

Разместить ManagerPlanner в Yandex Cloud по схеме, аналогичной TripPlanner: отдельный Serverless Container и отдельная база данных в существующем Yandex Managed PostgreSQL-кластере.

## Ограничения

- Railway и Supabase не отключать и не удалять до завершения миграции, тестирования и приемки.
- Новый PostgreSQL-кластер не создавать.
- Использовать существующий кластер, не смешивая данные ManagerPlanner и TripPlanner.
- Не менять DNS, домены и ресурсы TripPlanner.
- Сначала провести аудит, затем вносить точечные изменения.

## Подготовительный аудит

Проверить текущую ветку, `git status`, `package.json`, Dockerfile, `railway.json`, server/client/shared, конфигурацию базы, GitHub workflow, авторизацию, Railway-сервис, Supabase, существующий PostgreSQL-кластер, Container Registry и Serverless Container. Зафиксировать рабочее состояние Railway и возможность отката.

## База данных

1. Создать резервную копию Supabase.
2. Создать в существующем кластере отдельную базу или схему ManagerPlanner, отдельного пользователя и отдельные секреты.
3. Перенести структуру, индексы, внешние ключи, последовательности, ограничения, пользователей, роли, планы, фактические данные, справочники, настройки и историю.
4. Сохранить названия таблиц и колонок, если это не мешает запуску.
5. Сверить количества записей и контрольные выборки между Supabase и Yandex PostgreSQL.

## Production-подключение

Использовать явно выбранную Yandex-базу без незаметного fallback на Supabase:

```text
NODE_ENV=production
PORT=8080
DATABASE_TARGET=yandex
YANDEX_PG_HOST=...
YANDEX_PG_PORT=6432
YANDEX_PG_DATABASE=managerplanner
YANDEX_PG_USER=managerplanner_app
YANDEX_PG_PASSWORD=...
YANDEX_PG_SSL_CA_FILE=...
SESSION_SECRET=...
APP_BASE_URL=https://АДРЕС-MANAGERPLANNER
```

Секреты хранить в Lockbox или защищенной конфигурации Yandex Cloud. Не помещать их в GitHub, frontend, Excel или открытый `.env`.

## Авторизация

Сначала определить фактическую модель входа ManagerPlanner. Авторизацию не менять без диагностики. При использовании Яндекс 360 настроить отдельные callback и секреты ManagerPlanner. Проверить вход администратора и обычного пользователя, роли, отказ неизвестного пользователя, выход и повторный вход.

## Контейнер

Контейнер должен собираться из текущего репозитория, слушать `0.0.0.0`, использовать `process.env.PORT`, запускать production-сервер, не зависеть от локальных файлов, раздавать frontend и API, писать ошибки в Cloud Logging и иметь endpoint `/health`.

Ожидаемый ответ:

```json
{"status":"ok"}
```

## Проверки проекта

```text
npm install
npm run check
npm run build
git diff --check
```

Дополнительно проверить дублированные маршруты, миграции, загрузку файлов, фоновые задачи и абсолютные URL API.

## Публикация

1. Собрать образ ManagerPlanner.
2. Опубликовать образ в существующий Container Registry.
3. Использовать отдельный Serverless Container ManagerPlanner.
4. Не менять контейнер TripPlanner.
5. Добавить переменные окружения и секреты.
6. Создать новую ревизию и проверить ее до переключения.
7. Зафиксировать commit, image digest, revision ID, время публикации и целевую базу.

## Тесты после публикации

Проверить `/health`, подключение к Yandex PostgreSQL, сессии, входы, роли, выход, список менеджеров, создание и изменение планов, календарь, аналитику, справочники, экспорт, вложенные URL, компьютер, планшет и телефон. Убедиться в отсутствии запросов к неправильной базе, Railway API и старому Supabase Auth, если они не предусмотрены текущей моделью.

## Откат

При критической ошибке вернуть предыдущую ревизию Yandex Cloud, оставить пользователей на Railway, восстановить прежнее подключение и callback, не удалять новую базу, не менять рабочий Railway-сервис и сохранить логи.

## Критерии готовности

ManagerPlanner работает в Yandex Cloud, использует отдельную базу существующего PostgreSQL-кластера, данные перенесены без потерь, авторизация и роли работают, `/health` возвращает `status: ok`, основные функции проверены, откат подтвержден, Railway остается рабочим резервом.
